## 1. Core Philosophy

In Orbit, a **Hash** (or Checksum) is the unique, deterministic, and immutable digital fingerprint of a file's binary content.

- **Path-Agnostic:** Identifies content regardless of file name or on-disk directory location.
- **Primary Lookup Key:** Acts as the primary resolution key for cross-referencing with external databases (No-Intro, Redump, Hasheous, IGDB, TOSEC, RetroArch DATs) and for data integrity verification.
- **Cross-Cutting Standard:** Applied consistently across all library assets (Games, BIOS files, UserData, and Media).

---

## 2. Supported Algorithms

Orbit officially supports four hash algorithms:

| Algorithm | Primary Use Case | Standard Format |
| :--- | :--- | :--- |
| **CRC32** | Retro cart-based ROMs (No-Intro, GBA, NES, SNES, MegaDrive) | 8-character Uppercase Hex (e.g., `A1B2C3D4`) |
| **MD5** | General integrity checks & legacy databases | 32-character Lowercase Hex |
| **SHA1** | Disc-based media (Redump ISOs, PS1/PS2, Saturn), Hasheous API | 40-character Lowercase Hex |
| **SHA256** | Modern files, large binaries, high-security validation | 64-character Lowercase Hex |

## 3. File System Storage Standards (`checksum/`)

To respect Orbit's *File-System First* mandate, computed checksums are persisted directly on disk alongside the target assets.

### 3.1 Checksum File Naming Conventions

Checksum files adopt the following naming patterns:

- **Single File:** `<filename>.<algorithm>`  
  *Example:* `checksum/scph1001.bin.sha1`, `checksum/game.iso.md5`
- **Entire Folder / Content Bundle:** `content.checksum.<algorithm>`  
  *Example:* `checksum/content.checksum.sha1`
- **Pre-Conversion Original File:** `original.<original_filename>.<algorithm>`  
  *Examples:*  
  - `checksum/original.game.iso.sha1` (retains the SHA1 and exact filename of the source `.iso` file prior to conversion/compression).  
  - `checksum/original.Track 1.bin.sha1` (retains the SHA1 of an individual track in a multi-file CUE/BIN dump prior to CHD conversion).  
  *(Prepending `original.` keeps pre-conversion checksum files neatly grouped together in alphabetical directory listings).*

### 3.2 Content Format & Letter Casing

A checksum file contains **only** the raw hex string of the calculated hash, adhering to the following casing rules:

- **CRC32:** Written in **UPPERCASE** (e.g., `A1B2C3D4`), matching No-Intro, TOSEC, and RetroArch DAT standards.
- **MD5, SHA1, SHA256:** Written in **LOWERCASE** (e.g., `4b2a8f90...`), matching POSIX tool outputs (`sha1sum`, `md5sum`), Hasheous, and Redump standards.

**Comparison Policy (Case-Insensitive):**  
When reading checksum files or matching hashes against external databases, Orbit **always** performs case-insensitive comparisons (normalizing strings via `.toLowerCase()`) to prevent mismatch errors caused by third-party tools.

### 3.3 Location & Resolution Rules (Official vs Fallback)

Orbit enforces a dual-resolution policy for reading and writing checksum files:

1. **Official / Primary (Write & Read):**  
   All checksums generated by Orbit are written to a dedicated `checksum/` subfolder inside the target directory (e.g., `Games/<platform>/<game>/checksum/filename.sha1`). This keeps the root game folder clean and uncluttered.
2. **Fallback / Secondary (Read-Only):**  
   When resolving or verifying a file's checksum, Orbit checks `checksum/filename.<algorithm>` first. If missing, it checks for `filename.<algorithm>` directly in the same folder alongside the file.

### 3.4 Cross-Platform Filename Sanitization

When generating checksum filenames (especially for pre-conversion originals like `original.<original_filename>.<algorithm>`), Orbit applies standard cross-platform sanitization (`PathService.getSafeFolderName`) to strip illegal characters on Windows/Linux (`\ / : * ? " < > |`). This guarantees that checksum filenames remain 100% portable and safe across operating systems.

## 4. Compressed Archives (ZIP, 7z)

When Orbit processes compressed archives:

1. **Archive Hash:** The hash of the container archive file itself on disk (e.g., `puckman.zip`).
2. **Inner File Hash:** The uncompressed in-memory hash of entries inside the archive (used for No-Intro / MAME DAT matching).

## 5. Performance, Caching & Computation Strategy

### 5.1 Size-Based Computation Strategy

To optimize CPU and disk I/O performance:

- **Files < 1 GB:** Orbit computes **ALL** available algorithms (`CRC32`, `MD5`, `SHA1`, `SHA256`) simultaneously in a single streaming pass. Since the file is small, the I/O cost of calculating multiple hashes concurrently is negligible and provides complete database coverage.
- **Files ≥ 1 GB:** Orbit computes **ONLY** the **preferred hash algorithm** for that specific media type (typically **SHA1** for disc-based media like Redump ISOs/CHDs, or **SHA256** for PC dumps), avoiding unnecessary CPU and disk read overhead on multi-gigabyte files.

### 5.2 On-Demand (Lazy) Computation Policy

Computing hashes is **on-demand (lazy)**. Orbit does not force hash calculations for every loose file in heavy directories (such as PC game dumps or unmanaged sets). Checksums are computed and persisted only when explicitly requested, during game import/conversion, or when platform-specific verification rules require it.

### 5.3 Caching & Invalidation

- **Cache-First Reading:** Before starting hash calculations for large binaries (e.g., multi-gigabyte ISOs), Orbit checks if a valid checksum file already exists in `checksum/`.
- **Cache Invalidation:** If a target file's size (`size`) or modification timestamp (`mtime`) changes, existing cached checksums are marked invalid and recalculated.
